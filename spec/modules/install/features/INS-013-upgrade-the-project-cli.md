## Intent
Projects keep a pinned CLI at .spec/bin/spec so CI and non-Claude harnesses can use it. The plugin can update that copy without changing the project's spec or prompts.

## Behaviour
### S1: Install the pinned CLI when it is missing
Given an empty folder "repo" and a built CLI at a launcher with spec and spec.cjs beside it
When the user runs spec upgrade . through install.Upgrade
Then .spec/bin/spec and .spec/bin/spec.cjs are copies of the current launcher's files with mode 755
And install.ProjectCli.launcher and install.ProjectCli.bundle match the running CLI
And stdout is "upgraded .spec/bin/spec not installed → <version>" (R1)

### S2: Replace a different pinned version
Given .spec/bin/spec --version prints "spec 0.0.1" in repo and the running CLI is version <version> (R2)
When the user runs spec upgrade repo through install.Upgrade
Then both files in .spec/bin/ are copies of the running CLI's launcher and bundle
And install.ProjectCli is both files in .spec/bin/
And stdout is "upgraded .spec/bin/spec 0.0.1 → <version>" (R1)

### S3: Leave an up-to-date CLI alone
Given repo/.spec/bin/spec --version prints the running CLI's version <version>
And both files in repo/.spec/bin/ are byte-identical to the running CLI's launcher and bundle
When the user runs spec upgrade from "repo" through install.Upgrade without a repository argument
Then .spec/bin/ is unchanged (R1)
And the first line of stdout is "up to date <version>"

### S4: JSON output
Given repo/.spec/bin/spec --version prints "spec 0.0.1"
When the user runs spec upgrade repo --format json through install.Upgrade and the running CLI is version <version>
Then stdout is one JSON object with install.UpgradeResult.upgraded true, install.UpgradeResult.oldVersion "0.0.1" and install.UpgradeResult.version <version>

### S5: The explicit source wins
Given the project CLI is version 0.0.1 and source directories A and B hold versions 0.4.0 and 0.3.0
When the user runs `spec upgrade --from A` while `SPEC_PLUGIN_ROOT` names B through install.Upgrade
Then `.spec/bin/spec` and `.spec/bin/spec.cjs` copy A (R3)

### S6: Use the newest installed plugin
Given the installed plugin registry lists two user-scoped `spec@spec` installations, with B's `installedAt` later than A
When the user runs `spec upgrade` without `--from` or `SPEC_PLUGIN_ROOT`
Then `.spec/bin/spec` and `.spec/bin/spec.cjs` copy B (R3)

### S7: A project CLI cannot upgrade itself
Given the running launcher is the target project's own `.spec/bin/spec` and no plugin source is installed
When the user runs `spec upgrade`
Then it exits non-zero with `no newer spec found; run "${CLAUDE_PLUGIN_ROOT}/scripts/spec" upgrade from a Claude Code session`

### S8: Downgrade requires --force
Given the project CLI is version 0.2.0 and the selected source is version 0.1.0
When the user runs `spec upgrade --from <source>` without `--force`
Then the CLI stays unchanged and reports that `--force` is required (R4)

### S9: A forced downgrade is named
Given the project CLI is version 0.2.0 and the selected source is version 0.1.0
When the user runs `spec upgrade --from <source> --force`
Then both files are copied and stdout starts `downgraded .spec/bin/spec 0.2.0 → 0.1.0` (R4)

### S10: Old generated layout is migrated
Given repo contains an old-generated `.claude/skills/shop-spec/` install and its old settings entries
When the user runs `spec init repo --name shop` or `spec upgrade repo`
Then unchanged files generated by the old templates and known old CLI bundle are removed and each removal is reported
And edited or unknown files remain and are reported as `kept (edited): <path>` (R5)

### S14: An unchanged retired orchestrate skill is removed
Given `.claude/skills/orchestrate/SKILL.md` matches the old generated orchestrate skill for this project's CLI path
When the user runs `spec init repo --name shop` or `spec upgrade repo` through install.Upgrade
Then install.UpgradeResult.removed contains `.claude/skills/orchestrate/SKILL.md`
And `.claude/skills/orchestrate/` is removed if empty

### S15: An edited retired orchestrate skill is kept and reported
Given `.claude/skills/orchestrate/SKILL.md` differs from the old generated orchestrate skill
When the user runs `spec init repo --name shop` or `spec upgrade repo` through install.Upgrade
Then install.UpgradeResult.keptEdited contains `.claude/skills/orchestrate/SKILL.md`
And the skill remains unchanged

### S16: Removed hook entries are stripped from pinned CLI settings
Given `.claude/settings.json` has `permissions.defaultMode` "default" and hooks invoking `.spec/bin/spec hook claude-code before-delegate` and `before-finish`, plus active `session-start`, `after-edit` and unrelated hooks
When the user runs `spec upgrade repo` through install.Upgrade
Then the removed hook entries are absent
And the active and unrelated hooks and `permissions.defaultMode` remain unchanged

### S17: A newer unrelated project install does not outrank a user install
Given the registry has a user-scoped `spec@spec` entry and a newer project-scoped entry whose `projectPath` is another repository
When `spec upgrade` resolves its installed plugin source for this repository
Then it selects the user-scoped entry (R3)

### S18: A newer unrelated project install does not outrank this project's install
Given the registry has a `spec@spec` entry whose `projectPath` resolves to this repository and a newer project-scoped entry for another repository
When `spec upgrade` resolves its installed plugin source for this repository
Then it selects the matching project entry (R3)

### S20: Upgrade orders installed plugins by their latest update
Given eligible registry entries have both `lastUpdated` and `installedAt` timestamps, and a different entry is newer by `installedAt`
When `spec upgrade` resolves its installed plugin source
Then it selects the eligible entry with the latest `lastUpdated` (R3)
And when `lastUpdated` is absent, it orders eligible entries by `installedAt`

### S19: Upgrade preserves stored delegation values
Given the project stores Claude Code delegation values `claude-sonnet-5-5`, `inherit` and `opus-4` in shared and local config
When the user runs `spec upgrade`
Then both config files retain those values unchanged

### S21: A different build at the same version is replaced
Given repo/.spec/bin/spec --version prints the running CLI's version <version>
And repo/.spec/bin/spec.cjs differs in bytes from the running CLI's bundle
When the user runs spec upgrade repo through install.Upgrade
Then both files in .spec/bin/ are copies of the running CLI's launcher and bundle (R6)
And install.ProjectCli.launcher and install.ProjectCli.bundle match the running CLI
And the first line of stdout is "rebuilt .spec/bin/spec <version>" (R6)

### S22: A different launcher at the same version is replaced
Given repo/.spec/bin/spec --version prints the running CLI's version <version>
And repo/.spec/bin/spec differs in bytes from the running CLI's launcher while repo/.spec/bin/spec.cjs is identical to its bundle
When the user runs spec upgrade repo through install.Upgrade
Then both files in .spec/bin/ are copies of the running CLI's launcher and bundle (R6)
And the first line of stdout is "rebuilt .spec/bin/spec <version>" (R6)
And a pinned launcher that reports the running CLI's version does not keep its own bytes in place (INV-010)

### S23: A rebuild at the same version is named in JSON
Given repo/.spec/bin/spec --version prints the running CLI's version <version>
And repo/.spec/bin/spec.cjs differs in bytes from the running CLI's bundle
When the user runs spec upgrade repo --format json through install.Upgrade
Then stdout is one JSON object with install.UpgradeResult.upgraded true, install.UpgradeResult.rebuilt true, install.UpgradeResult.downgraded false, install.UpgradeResult.oldVersion <version> and install.UpgradeResult.version <version> (R6)

### S24: A rebuild at the same version needs no --force
Given repo/.spec/bin/spec --version prints the running CLI's version <version>
And repo/.spec/bin/spec.cjs differs in bytes from the selected source's bundle
When the user runs spec upgrade repo --from <source> through install.Upgrade without --force
Then both files in .spec/bin/ are copies of the source's launcher and bundle (R6)
And the first line of stdout is "rebuilt .spec/bin/spec <version>" and does not start with "downgraded" (R4)

### S25: A launcher left without its bundle is restored
Given repo/.spec/bin/spec exists and repo/.spec/bin/spec.cjs does not exist
When the user runs spec upgrade repo through install.Upgrade
Then repo/.spec/bin/spec.cjs is a copy of the running CLI's bundle with mode 755 (R6)
And repo/.spec/bin/spec is a copy of the running CLI's launcher

### S26: A different version is still reported by version
Given repo/.spec/bin/spec --version prints "spec 0.0.1" and repo/.spec/bin/spec.cjs differs in bytes from the running CLI's bundle
When the user runs spec upgrade repo through install.Upgrade
Then stdout is "upgraded .spec/bin/spec 0.0.1 → <version>" on its first line and install.UpgradeResult.rebuilt is false in the JSON form of the same run (R1)

### S27: An unreadable pinned version is replaced
Given repo/.spec/bin/spec exists but running it with --version fails (R2)
When the user runs spec upgrade repo --format json through install.Upgrade
Then stdout is one JSON object with install.UpgradeResult.upgraded true, install.UpgradeResult.oldVersion "unknown" and install.UpgradeResult.version <version>
And both files in .spec/bin/ are copies of the running CLI's launcher and bundle

### S28: A replacement leaves only the two pinned files
Given repo/.spec/bin/spec --version prints "spec 0.0.1"
When the user runs spec upgrade repo through install.Upgrade
Then the entries of repo/.spec/bin/ are exactly "spec" and "spec.cjs", both with mode 755 (R7)
And install.ProjectCli is both files in .spec/bin/

### S29: A bundle that cannot be copied leaves the old install
Given repo/.spec/bin/spec --version prints "spec 0.0.1" and the selected source's bundle cannot be read
When the user runs spec upgrade repo through install.Upgrade
Then the launcher and bundle in repo/.spec/bin/ are byte-identical to what they were (R7)
And the entries of repo/.spec/bin/ are still exactly "spec" and "spec.cjs"
And the exit code is 1 and the first line of stderr starts with "upgrade failed: " (R7)

### S30: A launcher that cannot be copied never leaves a launcher without its bundle
Given an empty folder "repo" and the selected source's launcher cannot be read
When the user runs spec upgrade repo through install.Upgrade
Then repo/.spec/bin/ holds no file: no spec, no spec.cjs and no temporary file (R7)
And the exit code is 1 and the first line of stderr starts with "upgrade failed: " (R7)

### S31: A write that fails part way leaves the old install and writes nothing else
Given repo/.spec/bin/spec --version prints "spec 0.0.1", repo contains an old-generated `.claude/skills/orchestrate/SKILL.md` and `.claude/settings.json`, and the disk becomes full while a new file is being written in repo/.spec/bin/
When the user runs spec upgrade repo through install.Upgrade
Then the launcher and bundle in repo/.spec/bin/ are byte-identical to what they were, and the entries of repo/.spec/bin/ are exactly "spec" and "spec.cjs" (R7)
And `.claude/skills/orchestrate/SKILL.md` and `.claude/settings.json` are byte-identical to what they were (R7)
And the exit code is 1 and the first line of stderr starts with "upgrade failed: " (R7)

### S32: A launcher that cannot be put in place after the bundle restores the old bundle
Given repo/.spec/bin/spec --version prints "spec 0.0.1", and the new launcher cannot be put in place after the new bundle has been
When the user runs spec upgrade repo through install.Upgrade
Then the launcher and bundle in repo/.spec/bin/ are byte-identical to what they were, and the entries of repo/.spec/bin/ are exactly "spec" and "spec.cjs" (R7)
And the exit code is 1 and the first line of stderr starts with "upgrade failed: " (R7)

### S33: A launcher that cannot be put in place on a fresh install leaves nothing
Given an empty folder "repo", and the new launcher cannot be put in place after the new bundle has been
When the user runs spec upgrade repo through install.Upgrade
Then repo/.spec/bin/ holds no file: no spec, no spec.cjs and no temporary file (R7)
And the exit code is 1 and the first line of stderr starts with "upgrade failed: " (R7)

### S34: A restore that fails too keeps the old bundle and says how to put it back
Given repo/.spec/bin/spec --version prints "spec 0.0.1", the new launcher cannot be put in place after the new bundle has been, and the old bundle cannot be put back either
When the user runs spec upgrade repo through install.Upgrade
Then the exit code is 1 and the first line of stderr starts with "upgrade failed: " and contains the error of the launcher that could not be put in place (R8)
And stderr contains the error of the failed restore and names a backup file in repo/.spec/bin/ (R8)
And that backup file is byte-identical to the old bundle, and the entries of repo/.spec/bin/ are exactly "spec", "spec.cjs" and that backup file (R8)
And the launcher in repo/.spec/bin/ is byte-identical to what it was (R8)
And one line of stderr contains both the backup file's name and "spec.cjs" and tells the user to move the backup over spec.cjs (R8)

### S35: Upgrade prefers the happyface plugin ID
Given the installed plugin registry lists a user-scoped `spec@happyface` installation A and a user-scoped `spec@spec` installation B whose `lastUpdated` is later than A's
When the user runs `spec upgrade` without `--from` or `SPEC_PLUGIN_ROOT`
Then `.spec/bin/spec` and `.spec/bin/spec.cjs` copy A (R3)
And when the registry's only `spec@happyface` installation is project-scoped to another repository, they copy B (R3)

## Rules
- R1: Upgrade copies both launcher and bundle from the selected source when the installed version differs; an identical version with identical bytes is up to date (R6 covers differing bytes)
- R2: Version is read by running the project's launcher with --version
- R3: Sources are tried in order: --from, SPEC_PLUGIN_ROOT/scripts, the newest eligible installed_plugins.json entry for spec@happyface, or for spec@spec when no spec@happyface entry is eligible (scope `user` or projectPath resolving to the target repository; INS-014/R15), then the running launcher folder unless it is the target project's .spec/bin. Eligible entries are ordered by `lastUpdated`, newest first, falling back to `installedAt` when it is absent.
- R4: A source older than the installed CLI requires --force; a forced downgrade is reported as downgraded
- R5: Migration removes a file only when its bytes match known old generated content; edited or unknown files are preserved and reported
- R6: When the installed version equals the selected source's version, upgrade compares the bytes of the launcher and of the bundle in .spec/bin/ with the source's; if either file differs or is missing it copies both and reports `rebuilt .spec/bin/spec <version>` with install.UpgradeResult.upgraded and install.UpgradeResult.rebuilt true and install.UpgradeResult.downgraded false, without --force. Identical bytes stay up to date, and a version difference is decided by R1 and R4 whatever the bytes.
- R7: Every replacement of the files in .spec/bin/ (R1, R6, an install) first writes both new files completely under temporary names in .spec/bin/, then renames the bundle into place and then the launcher. Two renames are not one step: between them a new bundle sits beside the old launcher, which is harmless because the launcher only loads the bundle beside it, and no launcher is ever without a working bundle. If any write or rename fails, upgrade restores the old files (the old bundle is kept aside until the launcher is in place; a fresh install is removed again), leaves no temporary file in .spec/bin/, writes nothing else (no migration, settings or other file changes), prints `upgrade failed: <error>` on stderr and exits with code 1 (not the usage-error code 2).
- R8: When an old bundle existed and upgrade cannot put it back after a failed replacement (R7), it keeps the copy it set aside in .spec/bin/ rather than deleting it, still leaves no temporary file, writes nothing else and exits with code 1. The first line of stderr is still `upgrade failed: <error>` with the error that started the rollback; stderr also carries the error of the failed restore, the backup file's name, and a line telling the user to move that backup over .spec/bin/spec.cjs by hand. The name is the one the message gives and is not otherwise fixed. A fresh install has no old bundle, so there is nothing to keep.

## Out of scope
- Updating the project spec or role prompts
