# The spec format (format 2)

The files under `spec/`, what each holds, and the rules lint enforces. `spec lint` names every
problem with its fix; this page is the overview. The decisions behind format 2 are DECISIONS
X86–X93 (first review round), X95–X104 (second), X105–X113 (third), X114–X121 (fourth) and
X122–X127 (fifth), X128–X133 (sixth), and X134–X136 (pilots on real code).

## Layout

```text
spec/
  config.json                    formatVersion, test command, globs, ticket store, delegation models
  config.local.json              optional local delegation overrides and unavailable models; gitignored
  core/overview.md               purpose and actors (free text)
  core/conventions.md            how this project writes scenarios and errors
  core/glossary.md               ### <Term> entries (or core/glossary/*.md for a large spec)
  core/invariants.md             ### INV-<NNN>: <title> entries (or core/invariants/*.md)
  modules/<module>/_module.md    id, prefix, domain, status (external: true for another system); what it owns
  modules/<module>/contracts.md  ### <module>.<Name> contracts (or contracts/*.md for a large module)
  modules/<module>/features/<ID>-<slug>.md
  decisions/ADR-<NNN>-<slug>.md
  ui/UI-<NNN>-<slug>.md
  index.md                       generated by spec build, committed
  _generated/graph.json          generated by spec build, ignored by git
```

`delegation` in `config.json` maps free-form harness names to models by stage role, for example
`{ "claude-code": { "implementer": "sonnet" }, "astro": { "reviewer": "opus" } }`. The stage roles
are `spec-writer`, `spec-review`, `tester`, `implementer` and `reviewer`; without a `spec-review`
model the spec review runs on the same harness's reviewer model, and its absence is never a lint
warning. Under `claude-code` a role may instead hold a list, best first, each model once:
`[{ "model": "sonnet", "effort": "high" }, { "model": "haiku" }]`, with an optional effort of `low`,
`medium`, `high`, `xhigh` or `max`. The first supported model not marked unavailable is chosen; its
effort is sent only when `claude --version` shows 2.1.292 or later.
`budgets` may set `brief.spec-review` (default 10000 tokens, not counting the spec delta). The
optional `config.local.json` has the same `delegation` shape, where a role replaces the shared role's
whole setting, and `unavailableModels`, for example `{ "opus": true }`, which marks Claude Code models
this machine cannot use (`config set unavailableModels.opus true --local`). It overrides nothing else,
is ignored by `spec/.gitignore`, and neither the project delegation map nor this local override changes the authored spec version.

`generated` is an optional object `{ "globs": [...], "command": "..." }` for the project's own
generated outputs. `globs` (at least one) extends the built-in generated paths (`spec/index.md`,
`spec/_generated/`, the pinned CLI and the legacy skill bundle). A conflict in one of these paths
takes the side being merged in (the ticket branch's copy in a merge, the base branch's in a sync)
instead of merging as text; spec rebuilds its own index and graph. `command` is optional: when set,
it runs once in the project root after such a conflict and rebuilds the files; without it nothing is
rebuilt and the side taken stands. Older pinned CLIs reject config keys they do not know: upgrade the
pin before adding or changing it.
Use non-empty globs without absolute paths, backslashes, or `.` / `..` path segments, and list only
files the project generates. Hand-written files should not be listed.

`generatedGlobs` is the older key for the same idea and stays accepted: it is read as more
`generated.globs` without a command, so a conflict only in its paths takes one side and runs no
command, even when `generated` sets one. Its globs follow the same rules. `spec lint` warns L036
while it is set; move its globs into `generated.globs` and remove it.

`enforce` optionally switches the edit, commit and history guards off separately; omitted keys default
to `true`. `enforce.bypass: "person"` refuses agent-context bypass requests; otherwise an agent needs
`--approved-by-person` after the person approves in-session. `enforceSince` is a git ref used as the first
baseline for `spec verify-history`; init sets it to the current HEAD so older history is outside the check.

## IDs

| Unit | ID | Notes |
| --- | --- | --- |
| feature | `PRV-002` | Prefix from the module that created it. The ID stays if the feature moves. |
| scenario, rule | `PRV-002/S3`, `PRV-002/R1` | Numbered inside the feature. |
| contract | `providers.ProviderConfig` | `<module>.<Name>`, defined in that module. |
| member | `providers.ProviderConfig.active` | One casing per spec, set in `core/conventions.md` (lowerCamel by default); each stack maps it, as it maps types. |
| invariant, decision, screen | `INV-001`, `ADR-001`, `UI-001` | Three or four digits. |

Every unit has a status:

| Status | Means | Links to it |
| --- | --- | --- |
| `active` | current | fine |
| `deprecated` | still served and still tested, but not for new use | a warning (L005); the gate lets work on it start |
| `removed` | a tombstone: it keeps the ID from reuse | an error (L005); the gate refuses it |

An ID is never reused.
- A removed scenario or rule goes into its feature's `retired:` list, and stays there:
  check-report refuses a spec stage that takes a number off it.
- Every other unit stays as a tombstone with `status: removed`, and `superseded_by` when
  something replaces it. A removed feature holds no scenarios: its numbers are all retired, its
  tests go with them, and `## Behaviour` says None. It keeps `id`, `title`, `module`, `status`,
  `superseded_by` and `retired`, and drops its links, since no step names them any more.
- A tombstone's `superseded_by` is history and is never edited; the chain may end at a removed
  unit. A deprecated unit's chain must reach a current unit, since its callers move there.
- check-report refuses a spec stage that deletes a unit any other way, and one that makes a
  removed unit live again: removal is final, and a new unit takes a new ID.
- A module's status covers what it holds: a live feature or contract in a removed module is an
  error, in a deprecated one a warning (L005), and the gate refuses work in a removed module.

## Features

```markdown
---
id: CRT-001
title: Edit the cart
module: cart
status: active
writes: [cart.Cart.lines]
provides: [cart.AddItem]
invariants: [INV-001]
retired: [S4]
---
## Intent
## Behaviour      ### S<n>: <title>, then Given / When / Then / And / But lines
## Rules          - R<n>: … lines, or None
## Out of scope   bullets, or None
```

The steps link the feature to every contract they name, and the frontmatter adds only what a step
cannot say (X134). Each link says what the feature's code does with a contract; lint checks that
the contract's kind fits, and that a step of the right kind cites it (L008; And and But count as
the step before):

| Link | Takes | Written or derived | Cited in |
| --- | --- | --- | --- |
| `writes` | entity, type | written: a Then checks a write and a read alike | a Then |
| `provides` | operation | written: implementing it, not calling it | the When that invokes it |
| `observes` | any kind | written: the test touches it, the code does not | any step |
| `reads` | entity, type | derived: any other entity or type a step names | any step |
| `calls` | operation | derived: any other operation | the When or Then |
| `consumes` | event, error | derived: one a When names, or only a Given | a Given or When |
| `emits` | event, error | derived: one a Then names, and no When | a Then |

- A contract the feature writes and also names in a Given or When is state it depends on, so it is
  read as well. Named only in a Then, it is the write being checked: "Then no conversation.Message
  is added".
- `observes` is for a contract the scenarios set up or check while the feature's code does not use
  it: an export test that plants an API key to prove it never leaks observes `settings.ApiKey`; a
  settings test that checks sending then fails observes `conversation.ProviderDisabled`, which
  another feature raises. Impact re-verifies observers like readers, but the derived module
  dependencies leave them out, so they show what the code depends on.
- A hand-written `reads`, `calls`, `consumes` or `emits` is a warning (L001): the steps already say
  it. Checked against 416 hand-written links in seven specs, the derivation got none wrong.

`invariants`, `decisions` and `ui` link other units. Leave out keys that would be empty.
Every written link is named in a step (L008).

When one feature's behaviour runs another's, they meet at an operation: the first `calls` it, the
second `provides` it (`providers.StreamReply`). An operation features call and none provides is a
warning (L012). Not every `When` needs one: a user action on a screen is a trigger too.

An invariant names what it constrains, and a step that checks it cites it:

```markdown
### INV-002: API keys never appear in logs, exports or error messages
Applies to: settings.ApiKey.secret
The secret part of an API key is used only to call its provider.
```

```markdown
Then the export does not contain "sk-claude-secret" (INV-002)
```

- Impact on a contract reaches the invariants that apply to it, with the scenarios that show them,
  and a brief that quotes the contract quotes those invariants, whether or not the feature lists them.
- Impact on the invariant reaches the scenarios that cite it; in a feature where no step cites it,
  every scenario. A cited invariant must be in `invariants:`.
- A scenario shows an invariant by citing it, or a rule that cites it. One no scenario shows is a
  warning (L025); one that changes while none of its scenarios does is refused at the spec stage.
- An invariant no scenario can show (a latency budget, an accessibility review) says how it is
  checked instead: `Shown by: the load benchmark in CI`.

A step that shows a rule cites it: `Then "mistral" is never called (R2)`, or `(INV-001, R1)`. A
rule no scenario cites is a warning (L023); a rule that changes while none of its scenarios does
is refused at the spec stage.

A step may carry data: a table (lines starting `|`) or a fenced block right under it. It is part
of the step, its IDs are cites, and changing it changes the scenario. A quoted string, in a step
or its data, is a value and never a cite: `Then the export is "vendor.Cancelled"` names nothing.

```markdown
Then cart.Cart.lines holds (R1):
| name | priceCents | quantity |
| apple | 120 | 2 |
```

A scenario's behaviour is its steps and their data. A new title over the same steps is a
rewording: briefs list it, but the tester need not show it failing first. A screen's behaviour is
its `## States` and `## Copy`; a change to its `## Layout` alone is a rewording too. A screen whose
states or copy change while none of the scenarios citing it does is refused at the spec stage.

## Contracts

```markdown
### providers.ProviderId
Kind: type · Status: active
Names one fake provider. Type: "claude" | "gpt" | "mistral"

### providers.RateLimited
Kind: event · Status: active
The provider refused a request because of rate limits.

#### providers.RateLimited.providerId
The provider that refused. Type: providers.ProviderId

### cart.AddItem
Kind: operation · Status: active
Adds a line to the cart.
Code: Cart.add
Output: null | cart.InvalidQuantity
```

- Kinds: `entity`, `event`, `operation`, `type`, `error`.
- Members are `####` headings under any kind, each with a one-line description and a `Type:`.
  An operation's members are its inputs, and its result is an `Output:` line. A member without a
  `Type:` is an error (L022).
- Each kind has one shape (L022): a `type` is a `Type:` expression or a record of members, never
  both; an `entity`, `event` or `error` is its members; an `operation` is its members and an
  `Output:`.
- `Code:` names the symbol that implements the contract, never its signature: an operation's
  inputs are its members, so a parameter list would say them twice, in one stack's syntax (L001).
  A tester calls the symbol with the members as its arguments. `spec lint --ci` warns (L024), and
  `spec gaps` reports, a `Code:` line whose owner and name (`Cart`, `add`) no code file holds
  together, so a rename in the code shows up.
- One feature `provides` an operation; two providers are a warning (L012).
- `Decisions: ADR-001` links the decisions behind a contract or an invariant.
- An error is a contract too: the feature that fails with it `emits` it, and the step says
  "fails with cart.InvalidQuantity".
- An ID written in prose (a description, Out of scope, an ADR) is for the reader and makes no
  link, but it must name a unit that exists (L026, a warning). Ticket IDs are not checked, and a
  feature-shaped name counts only with one of this spec's prefixes, so `SHA-256` is just text.

Another system's API is a module of its own with `external: true` in `_module.md`. It records the
contracts this product uses, as it uses them. It holds no features; features `call` its
operations and `consume` its events and errors. None `provides` its operations or `emits` its
events (L004), so a called operation needs no provider here (L012). A feature may `emit` one of
its errors: an operation of this product can pass a declined charge on to its caller.

## Types

`Type:` and `Output:` use one notation, whatever the stack (L022):

| Write | For |
| --- | --- |
| `string int number decimal bool bytes date datetime duration null` | primitives; `decimal` is exact (money), `number` is not |
| `"rate_limited"`, `3` | literals, for closed sets: `"done" \| "user"` |
| `providers.ProviderId` | a contract the spec defines |
| `T[]`, `map<K, V>`, `A \| B`, `(A \| B)[]` | lists, maps, unions |
| `T?`, `(A \| B)?` | on a member: it may be left out |

- Absent and null differ. `T?` is a member that may be left out; `T | null` is always there and
  may be null. `?` covers the whole type, so a union takes parentheses.
- A shape with named keys is its own `Kind: type` contract with members, never `{ … }` inline:
  its keys then have IDs that features and impact can name.
- A member has one `Type:` line, and a contract one `Type:` or `Output:` (L022): two would be two
  answers, and a merge can leave both.
- A quoted literal is a value, never a reference: `"vendor.Cancelled"` names no contract.
- Native spellings (`List<int>`, `String`, `Optional<T>`) are refused with the portable form as
  the fix. Where a native name means different things in different stacks, the fix names each
  reading: `Optional<string>` is `string?` (may be absent) or `string | null` (may be null). Each stack maps the notation once: `int` is `int` in Dart and Go, `number` in
  TypeScript; `T[]` is `List<T>` in Dart and `[]T` in Go; `map<K, V>` is `Map<K, V>` or `map[K]V`.
- A qualified name in a type is a `uses` link: impact on the type reaches every contract typed by
  it, and every feature using those. Only types link; an ID in a description is for the reader.

## Decisions

A decision (`decisions/ADR-<NNN>-<slug>.md`) has its own statuses: `accepted`, which reads as
active, and `superseded`, which reads as removed. It has no `deprecated`. `supersedes` names one
decision or a list of them, and `superseded_by` names the one that replaced it. Its sections come
in this order: `## Decision`, `## Consequences`, `## Context`, `## Alternatives` (L006).

## Screens

A screen (`ui/UI-<NNN>-<slug>.md`) has `## Layout`, `## States` and an optional `## Copy`. Its
frontmatter may name what it renders and what its controls call; impact on those contracts, or on
a feature that produces them, then reaches the screen:

```yaml
shows: [providers.FallbackTriggered]   # entities, types, events, errors (and members)
calls: [cart.AddItem]                  # operations
image: card.png                        # optional: a picture of the screen, under ui/ (L004 if missing)
```

## Generated files

`spec build` writes `index.md` and `_generated/graph.json`. Only `index.md` is committed: it holds
no hash and no line numbers, so it changes only when a module or a feature's title or status does.
`spec lint --ci` checks that it is fresh, and `spec merge` rebuilds it rather than merging it, so
two branches that both change it never need a person. The graph also holds each module's dependencies,
derived from the contracts its features' code uses (every link but `observes`).

Each project keeps its pinned CLI at `.spec/bin/spec` and `.spec/bin/spec.cjs`; `spec upgrade`
replaces that copy from the running plugin when its version differs. This repository commits the
plugin bundle under `plugin/scripts/`; `npm run build` rebuilds it along with `dist/`.

## From format 1

A format 1 spec has no `formatVersion`; lint says so. To migrate:

1. Add `"formatVersion": 2` to `config.json`.
2. Remove `depends_on` from every `_module.md`, and the `## Modules` list from `core/overview.md`.
3. Turn each `Payload:` or `Input:` list into `####` members with a `Type:` line.
4. Write every `Type:` in the spec's notation: define each shared type, and each inline object,
   as a `Kind: type` contract, and write it qualified. L022 lists every type to fix.
5. Define each error value as a `Kind: error` contract, and name it in the step that fails with it.
6. Move each operation a feature implements from `writes` to `provides`. Delete `reads`, `calls`,
   `consumes` and `emits` from every feature (L001 lists them): the steps state them. Where a
   scenario only sets up or checks a contract the feature's code does not use, list it under
   `observes`. L004 lists every written link whose kind does not fit.
7. Turn each `In code: …` into its own `Code: …` line, and each invariant's `Why:` into
   `Decisions:` (L001 lists both). Remove `requires:` from features.
8. Rename each tombstone's `status: deprecated` to `status: removed`; keep `deprecated` only for
   what is still served. Cite each rule from the scenario that shows it (L023 lists the rest).
9. Delete the `ID patterns` section from `core/conventions.md`, add `_generated/` to
   `spec/.gitignore`, remove `_generated/graph.json` from git, and run `spec build`.

A format 2 spec written before X134 still lints and means the same: its `reads`, `calls`,
`consumes` and `emits` lines are kept (a written link wins over a derived one) and each warns until
it is deleted.
